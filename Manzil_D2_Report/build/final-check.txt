Abstract

Manzil is a simulation-based research and development prototype for adaptive urban traffic control and
emergency routing. It combines video-based vehicle detection and tracking, traffic-state estimation,
comparative signal-control policies, congestion-aware ambulance routing, and a moving green corridor
within a SUMO test environment. A React dashboard and FastAPI services are proposed to expose
system state and experimental records. This report specifies the requirements, research method, archi-
tecture, and controlled evaluation protocol; implementation and measured results remain subsequent
project work.
                                                                                                          iii


Executive Summary

Urban road demand changes over time and between approaches, whereas a fixed timing plan cannot
respond to every short-term imbalance. Emergency vehicles face a related but stricter problem: a ge-
ographically short route can still be slow when queues, signal delay, or an incident obstruct the path.
Manzil studies these two problems in one controlled prototype. The system is intended to compare
fixed-time, rule-based adaptive, and reinforcement-learning signal control, then determine the contribu-
tion of dynamic routing and a moving green corridor to ambulance travel while measuring the disruption
imposed on ordinary traffic.

The project deliberately separates two evidence paths. Recorded traffic video is used to study whether a
detector and multi-object tracker can produce observable counts, speeds, and queue proxies. SUMO and
TraCI provide exact, repeatable network state for controller and routing experiments. These paths share
a versioned traffic-state contract, but this report does not claim that arbitrary camera footage reconstructs
a complete road network. Camera calibration, lane mapping, observation freshness, and uncertainty are
explicit constraints.

The proposed system uses a React dashboard, FastAPI application services, a background perception
worker, a SUMO/TraCI adapter, controller and routing services, and persistent experimental records.
PostgreSQL is a proposed persistence choice rather than a confirmed implementation fact. A selected,
manageable urban network is to be imported from OpenStreetMap and cleaned in SUMO NetEdit, with a
synthetic grid retained as a fallback. The core emergency case contains one active ambulance. Dynamic
edge costs combine estimated travel time, queue and signal delay without treating distance alone as the
objective. Priority is activated only for the next relevant intersections, uses safe clearance transitions,
detects passage, and then restores normal operation.

Evaluation is planned as matched, repeated simulation runs under light, medium, and heavy demand.
Normal traffic experiments compare the three controllers using travel time, waiting time, queue length,
throughput, and starvation checks. Emergency experiments compare an unassisted reference, congestion-
aware routing, and routing with corridor control using ambulance travel time and stops together with
normal-traffic delay and recovery time. Training and tuning scenarios will be separated from held-out
evaluation scenarios, and all configurations, random seeds, software versions, and failures will be re-
tained. No performance values are reported at this Deliverable 2 stage.

This report covers the project vision, a critical review of relevant research, software requirements, the
proposed research method, and high- and low-level design. Its main contribution at this stage is a
traceable and reproducible specification for investigating an integrated traffic-control and emergency-

Chapter 1 Introduction

Urban traffic control is a networked decision problem. Demand can change by approach, queue spillback
at one junction can obstruct another, and a timing plan that is adequate in one period may waste capacity
in another. Emergency travel adds a stricter timing objective. An ambulance does not benefit merely
from a short geometric path if that path contains slow links, long queues, or signals that repeatedly
stop it. These observations motivate Manzil, a research and development prototype that studies traffic
perception, adaptive signal control, congestion-aware emergency routing, and coordinated signal priority
in one simulation-based environment.

Manzil is not presented as a deployable municipal controller. It is a controlled experimental platform
based on the microscopic traffic simulator SUMO and its TraCI interface [1, 2]. The platform is intended
to make policies repeatable, observable, and comparable before any real-world actuation is considered.
Recorded video supplies a second, deliberately bounded input mode for studying whether vehicle detec-
tion and tracking can produce useful traffic indicators. The simulator remains the authoritative source of
network state in routing and signal-control experiments.



1.1    Purpose of this Document

This Deliverable 2 report translates the approved proposal into a traceable research and software design.
It defines the questions to be investigated, reviews the evidence behind major design choices, specifies
externally visible requirements, and describes the methodology and architecture needed to conduct fair
experiments. It also records the distinction between confirmed project scope, proposed technical choices,
and future implementation work.

The report does not claim experimental improvements, real-time performance, model accuracy, or de-
ployment readiness. At the proposal stage the problem definition, major functions, and conceptual archi-
tecture were established; dataset preparation, implementation, tuning, and evaluation were still planned
work. The methodology therefore defines how later claims must be produced rather than anticipating
their outcome.

The primary audience is the FAST–NUCES FYP supervisor and evaluation panel. They require enough
detail to judge research relevance, software scope, feasibility, and the validity of the proposed evaluation.
The report is also written for the student implementation team, who should be able to derive interfaces,
experiment configurations, and acceptance checks from it. A secondary audience consists of traffic-

Chapter 2 Project Vision

This chapter converts the broad motivation into a bounded project vision. It identifies the decisions
Manzil will make, the evidence needed to judge those decisions, and the conditions under which con-
clusions will remain limited to simulation and selected video.



2.1    Problem Domain Overview

Traffic-signal control allocates time among incompatible movements. Fixed plans are understandable
and easy to reproduce, but cannot react to short-term imbalance. Adaptive control can use measured
demand, yet an apparently efficient policy can be unfair if a lightly loaded approach waits indefinitely.
Network coordination complicates the problem because an action at one intersection changes arrivals at
downstream intersections.

Emergency routing operates on the same network but has a different objective. A route is useful only
when its costs reflect current travel time and intersection delay. Signal priority can reduce stops, but
careless preemption can create unsafe phase changes or long recovery queues. The project therefore
treats route selection, priority activation, passage detection, and recovery as one lifecycle while retaining
separate measurements for the ambulance and ordinary traffic.

2.2      Problem Statement

The project addresses the absence, within the selected prototype setting, of a reproducible way to com-
pare traffic-signal strategies and to quantify the combined effect of congestion-aware ambulance routing
and coordinated signal priority. The problem is to design a system that observes or simulates traffic
state, makes bounded control and routing decisions, records their causes and outcomes, and supports
fair comparison without claiming that simulation results transfer directly to a deployed city.



2.3      Problem Elaboration

Five linked sub-problems must be controlled. First, detections must be associated over time so that
frame-level boxes can become counts, trajectories, and lane-region observations. Second, normal signal
control requires fixed and adaptive baselines before RL is meaningful. Third, route costs must use
consistent units and must not count congestion twice. Fourth, the corridor must anticipate an ambulance
without holding unnecessary intersections green. Fifth, all comparisons must use matched demand,
seeds, and configurations.

An error can cross module boundaries. A stale observation may alter an edge cost; a route change
may invalidate planned signal priority; a prolonged priority phase may improve ambulance time while
worsening ordinary traffic; and an uncontrolled simulation clock may allow different services to act on
different steps. The vision therefore includes explicit freshness, ownership, fallback, and audit require-
ments.



2.4      Research Questions

RQ1        With declared video sources and annotations, how accurately and consistently can the pro-
           posed detector-tracker pipeline estimate observable vehicle counts and queue-related indica-
           tors?

RQ2        Under matched SUMO demand scenarios, how do fixed-time, rule-based adaptive, and a
           selected RL controller differ in waiting time, queue length, travel time, throughput, and ap-
           proach fairness?

RQ3        Holding signal control constant, what change in ambulance travel time, stops, and route sta-
           bility is attributable to dynamic congestion-aware routing?

RQ4        Holding routing logic constant, what additional emergency benefit and ordinary-traffic dis-
           ruption result from the moving green corridor?
CHAPTER 2. PROJECT VISION                                                                            7


RQ5        How sensitive are the conclusions to demand level, incident placement, random seed, and
           observation uncertainty?

These questions avoid a single vague claim of “better traffic.” Each comparison names a controlled
factor and paired outcome measures.



2.5    Goals and Objectives

The goal is to develop and evaluate a simulation-based intelligent traffic-management prototype that
supports normal traffic control and a single emergency mission. The measurable objectives are:

 O1. Define and implement a versioned traffic-state representation shared by perception, simulation,
      control, routing, and visualization.

 O2. Evaluate a pretrained vehicle detector with multi-object tracking on held-out, source-separated
      traffic-video segments.

 O3. Construct a manageable multi-intersection SUMO network and repeatable demand scenarios.

 O4. Implement fixed-time and reproducible rule-adaptive controllers, followed by one feasible RL
      controller.

 O5. Compute valid ambulance routes using time-based dynamic edge costs and bounded rerouting.

 O6. Coordinate safe, moving signal priority and restore normal control after passage or cancellation.

 O7. Provide a React dashboard and FastAPI service boundary for scenario control, monitoring, and
      experiment comparison.

 O8. Record configurations and outcomes so each reported run can be reproduced and audited.

2.7    Sustainable Development Goals

Manzil aligns principally with United Nations Sustainable Development Goal 11, which concerns in-
clusive, safe, resilient, and sustainable cities [4]. The project investigates more efficient use of existing
intersection capacity and more timely emergency movement, but it does not claim city-level impact from
a simulator. A secondary connection exists with health outcomes because ambulance delay can matter,
although the project neither measures clinical outcomes nor models medical priority.



2.8    Constraints and Assumptions

The main constraints are a semester-scale implementation window, limited access to local calibrated
traffic data, camera occlusion and perspective, the simulation-to-reality gap, and finite training hardware.
The selected network must therefore remain small enough for repeated trials. A real urban extract is
preferred, but a controlled grid is an acceptable fallback if map signal logic is incomplete.

The core experiments assume one active ambulance, valid origin and destination edges, controlled traffic

generation, and no direct actuation of public infrastructure. Video-derived queue length is an observable
proxy unless the scene is calibrated. PostgreSQL, the precise tracker, the RL algorithm, and computing

2.9     Business and Practical Opportunity

The prototype’s practical value is as a decision-support and experimentation environment. It can demon-
strate how policies react to repeatable congestion and emergency scenarios, help compare controller de-
signs, and expose the cost imposed on non-priority traffic. Any commercial or public-sector opportunity
would require validated local data, authority approval, hardware integration, cybersecurity assessment,
safety engineering, and field trials. No partnership, deployment commitment, or revenue expectation is
assumed.

Chapter 3 Literature Review and Related Work

This chapter examines the research needed to justify Manzil’s design rather than treating the use of fa-
miliar tools as a contribution. The review is organized around five decisions: how traffic is observed,
how normal signals are controlled, how learned policies are evaluated, how emergency routes are se-
lected, and how signal priority is activated and recovered. Reported results are interpreted within their
original datasets and environments; values from incompatible benchmarks are not compared as though
they were a common test.



3.1     Review Method and Terminology

The approved proposal provided an initial bibliography. Each retained study was checked against a
publisher page, proceedings record, DOI, or official open-access paper. Studies were selected for direct
relevance to detection and tracking, traffic-signal control, shortest-path routing, emergency routing, pre-
emption, or simulation. Official software documentation is used for interfaces but is not counted among
the research studies.

The review distinguishes detection from tracking. Detection locates and classifies objects in a frame;
tracking associates those observations through time. It also distinguishes priority from preemption. Pri-
ority may adjust normal timing within constraints, whereas preemption interrupts normal operation for
an emergency request. Manzil uses “corridor” for a coordinated sequence of such bounded interventions.



3.2     Vision-Based Traffic Observation

3.2.1   One-Stage Object Detection

Redmon et al. formulated YOLO as a single network that predicts bounding boxes and class probabilities
from an image in one evaluation [5]. The work established the feasibility of real-time one-stage detection
and reported strong speed, while also identifying localization errors as a relative weakness. For Manzil,
this supports a pretrained one-stage detector as a feasible starting point, not an assumption that all vehicle
classes and viewpoints will be accurate. A detector checkpoint must be evaluated on the selected traffic
scenes, and confidence thresholds cannot be copied from an unrelated benchmark.

The practical relevance is latency and a simple inference path. The limitation is that frame-level boxes do
not provide stable counts by themselves. Repeatedly counting the same vehicle, missed detections under
occlusion, and perspective-dependent apparent size require tracking and region rules. Manzil therefore
treats the detector as one stage in a measurement pipeline.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                             12


3.2.2   Multi-Object Association

Wojke et al. extended a simple online tracker with a learned appearance metric, improving association
through longer occlusions [6]. The method illustrates a tradeoff: appearance information can reduce
identity switches but adds a feature-extraction model and domain sensitivity. It is a useful alternative if
traffic identities fragment severely, but its additional cost must be justified by the metrics that Manzil
actually needs.

ByteTrack instead associates high-confidence detections first and then attempts to recover objects from
lower-confidence detections rather than discarding them [7]. The authors evaluated the approach across
multiple tracking benchmarks and reported strong MOT17 accuracy with real-time throughput on their
specified hardware. This is relevant because traffic occlusion often lowers confidence. Its benchmark
speed cannot be adopted as Manzil’s performance target, and an identity-preserving tracker does not by
itself determine lane membership or queue state.

Together, these studies motivate an empirical tracker selection. The decision should be based on count
error, identity stability where needed, and end-to-end throughput on the team’s hardware. If aggregate
counts are reliable without expensive appearance features, the simpler configuration may be preferable.


3.2.3   Traffic Datasets and Domain Coverage

BDD100K provides a large and diverse driving dataset with multiple tasks, including detection and
tracking, collected across varied locations, weather, and times [8]. This diversity is useful for initializ-
ing or stress-testing a perception pipeline. The camera perspective is primarily vehicle-mounted, how-
ever, whereas Manzil may use roadside or elevated recorded video. The dataset cannot substitute for
validation on the intended viewpoint.

UA-DETRAC is a benchmark focused on vehicle detection and tracking in traffic-surveillance video [9].
Its fixed-camera scenes are closer to an intersection-observation use case and its protocol makes detector-
tracker interactions visible. Its scenes still do not guarantee representation of Lahore traffic composition,
motorcycle density, rickshaws, lane discipline, or camera mounting. The strongest plan is therefore
to use licensed public material for reproducible comparison and a small, separately documented local
sample for domain analysis if collection is feasible and ethically permitted.

These dataset studies also shape data splitting. Adjacent video frames are highly correlated. Random
frame splitting can leak nearly identical scenes into training and test sets. Manzil will split by sequence
or source and will retain a held-out set that is not used for threshold tuning.

3.3     Conventional and Adaptive Signal Control

3.3.1   Fixed-Time Baseline

A fixed-time controller remains necessary even when it is not expected to dominate every scenario. It
supplies a stable reference, exposes whether demand generation itself is biased, and enables exact re-
production. The plan will specify phases, yellow and all-red transitions, cycle length, offsets if any, and
demand assumptions. A weak or arbitrarily misconfigured fixed baseline would exaggerate improve-
ments and undermine the comparison.


3.3.2   Max-Pressure Control

Varaiya formalized max-pressure control for networks of signalized intersections [10]. Pressure is de-
rived from upstream and downstream queue conditions, and selecting phases that reduce network pres-
sure has a stronger theoretical basis than using an unexplained weighted score. The method is decentral-
ized and responsive, which makes it a valuable non-learning reference.

Its assumptions and measurements still matter. Queue observations must be available, movements and
saturation behavior must be represented correctly, and phase switching must respect minimum green and
clearance. Manzil’s first rule-based controller will be deliberately transparent; a max-pressure-inspired
score is a stronger candidate than ad hoc percentages if the required downstream queues are reliable.
Fairness and maximum-red safeguards remain explicit even when pressure is used.



3.4     Reinforcement Learning for Traffic Signals

3.4.1   Cycle-Level Deep Q-Learning

Liang et al. used deep reinforcement learning to adjust traffic-light cycle behavior from traffic state [11].
The study demonstrates how state observations and action granularity can be connected to a learned
controller. It also illustrates a recurring limitation: a policy evaluated in a particular intersection and
demand setting may not generalize to unseen networks or demand distributions.

For Manzil, deep Q-learning is feasible only after the action space has been bounded and a stable baseline
exists. The report does not commit to reproducing the paper’s network or treating its reported improve-
ment as a project expectation. The applicable lesson is to define decision interval, phase legality, and
reward terms before training.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                           14


3.4.2   Pressure-Informed Reward Design

PressLight connects an RL reward and state representation to max-pressure traffic theory [12]. The paper
argues that a transportation-grounded reward reduces dependence on arbitrary handcrafted objectives
and evaluates the method against conventional and learning baselines in arterial settings. This is directly
relevant to Manzil because a reward based only on total waiting time can obscure spillback or starvation.

PressLight does not remove the need for careful evaluation. Network topology, flows, phase definitions,
and training budget influence performance. Manzil can use pressure as a principal reward signal or
baseline concept, but it must report the exact state and movement mapping. Emergency priority will be
implemented as a safety-constrained supervisory mode rather than silently folded into normal-controller
reward during the first comparison.


3.4.3   Phase Competition and Network Cooperation

FRAP represents competition among phases and was designed to exploit invariance across phase con-
figurations [13]. This is valuable where equivalent movements should not require independent learning
from scratch. Its structured representation increases implementation complexity and still depends on
an accurate phase graph. Manzil may adopt its representational lesson without claiming to reproduce
FRAP.

CoLight uses graph-attention mechanisms to support cooperation among intersections [14]. The study
addresses the limitation of isolated agents by allowing neighboring traffic information to influence de-
cisions. Such coordination is relevant for a multi-intersection corridor, yet attention-based multi-agent
training can exceed an undergraduate project’s tuning budget and complicate attribution. The initial
RL scope should therefore use either a centralized policy for a small network or a clearly defined
independent-agent arrangement, with coordination as a measured design choice.

Chu et al. studied multi-agent deep RL for larger signal networks and emphasized scalable coordination
[15]. Like CoLight, the work supports the importance of communication and local observations. It also
reinforces the risk of non-stationarity: when multiple agents update policies, each agent experiences an
environment affected by changing peers. Manzil should not claim network-level RL simply because
multiple signals exist; the policy ownership and training scheme must be explicit.


3.4.4   Simulation Environments

CityFlow was introduced as a multi-agent RL environment for large-scale city traffic scenarios [16].
Its contribution is chiefly simulation throughput and support for large networks. SUMO is retained
for Manzil because the proposal already depends on its microscopic model, traffic-light control, map
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                              15


toolchain, and TraCI integration [1]. CityFlow remains an important alternative in the design tradeoff:
it may train faster in some large-scale settings, but switching simulators would add model-equivalence
work and reduce alignment with the approved proposal.

Lopez et al. describe SUMO’s architecture and microscopic simulation capabilities [1]. Simulation
provides repeatability and access to internal state, but a simulator is not a validation of real-world impact.
Car-following parameters, route demand, signal programs, and map cleanup can materially affect results.
Manzil will version those artifacts and frame its conclusions as performance within declared simulation
conditions.



3.5    Dynamic Routing

Dijkstra’s shortest-path method finds minimum-cost paths on a graph with nonnegative edge weights
[17]. Hart, Nilsson, and Raphael introduced the formal basis of A*, which adds a heuristic estimate to
guide the search [3]. These algorithms are well established; using them is not Manzil’s novelty. The
project-specific work is the definition and update of valid edge costs, the treatment of closures, and the
interaction between routing and signal priority.

For time-dependent routing, physical distance is insufficient. Manzil proposes expected link travel time
plus non-overlapping estimates of queue discharge and residual signal delay. Each term must be ex-
pressed in seconds, or normalized with a documented interpretation. If travel time already includes
observed queue delay, adding a second congestion penalty would double-count the same effect. Dijkstra
is the reference implementation. A* may be used when a lower-bound free-flow travel-time heuristic
remains admissible under nonnegative added delays.

Dynamic rerouting can itself be harmful if small fluctuations repeatedly switch the route. The selected
path will be changed only when the remaining cost improvement exceeds a threshold and persists for a
defined interval, or when the current route becomes infeasible. Route revisions and computation time
are part of evaluation, not merely logs.



3.6    Emergency Routing and Signal Preemption

Humagain et al. systematically reviewed emergency-vehicle route optimization and preemption methods
[18]. The review identifies recurring gaps: limited real-world application, insufficient use of dynamic
traffic data, weak treatment of travel time, effects on general traffic, and safety. This supports Manzil’s
integrated evaluation, but it does not justify a claim that no integrated systems exist. It also motivates
measuring ordinary-traffic disruption alongside emergency benefit.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                            16


Qin and Khan studied transitions into emergency preemption and recovery to normal timing [19]. Their
work explicitly addresses safe clearance, use of otherwise unnecessary green time, and recovery queues.
The key design lesson is that preemption is a lifecycle rather than a single “set green” command. Manzil
therefore models requested, safe-transition, active, passage, and recovery states, and retains timing val-
ues as configurable simulation policies rather than certified field parameters.

Louati et al. investigated multi-agent, queue-aware emergency crossing at signalized intersections [20].
Queue-aware prioritization is relevant because a green indication alone does not guarantee an unob-
structed approach. The method is more ambitious than Manzil’s core single-ambulance case, but it
motivates look-ahead activation and checking whether downstream storage is available. Manzil will not
infer safety merely from the absence of simulated collisions.



3.7    Synthesis and Research Gap

The literature establishes reliable building blocks, but also exposes integration risks. One-stage detection
is fast enough to investigate traffic video, yet traffic indicators require tracking, geometry, and local
validation. Max-pressure and RL research offers responsive control, yet comparison is sensitive to state,
reward, phase constraints, and simulator assumptions. Shortest-path algorithms are mature, yet their
usefulness depends on dynamic costs and route-stability rules. Emergency-preemption research stresses
transition and recovery, yet ordinary-traffic impact is often a central tradeoff.

Manzil’s proposed contribution is therefore not a new detector, shortest-path algorithm, or RL family.
It is the design and controlled evaluation of an integrated, traceable prototype in which: (1) perception
and simulator evidence are not conflated; (2) normal controllers are compared under matched scenarios;
(3) routing and corridor contributions are ablated; and (4) ambulance benefit is reported together with
network disruption and recovery. The unresolved research question is whether this integration produces
consistent benefit under the selected scenarios and constraints.

3.8       Conclusion

The review supports a conservative technical strategy: start with transparent baselines, define mea-
surements before optimization, select one feasible RL formulation, and model emergency priority as a
stateful safety-constrained intervention. It also establishes the need for source-separated video evalu-
ation, matched simulation seeds, ablation of routing and corridor effects, and explicit external-validity
limits.

Chapter 4 Software Requirement Specifications

This chapter specifies the behavior required of the Manzil research prototype. Requirements are testable
where current evidence permits; numerical values that require benchmarking are explicitly identified
as design targets. The specification avoids account management, enforcement, and other modules not
justified by the approved scope.



4.1     System Features

The prototype is divided into six feature groups:

   1. Scenario management: select a network, demand profile, controller, seed, incident, duration, and
       emergency mission.

   2. Traffic perception: process licensed recorded video into detections, tracks, lane-region observa-
       tions, and aggregate measures with timestamps and confidence.

   3. Simulation and normal control: step SUMO through a single owner, read traffic state, apply
       fixed or adaptive actions, and preserve legal phase transitions.

   4. Emergency routing and corridor: validate origin and destination, compute dynamic paths, apply
       stable rerouting, activate moving priority, detect passage, and recover.

   5. Monitoring: show map state, signals, traffic indicators, ambulance route, corridor state, warnings,
       and data-source mode.

   6. Experiment records: persist immutable configuration, run events, aggregate metrics, software
       versions, seed, and termination state for comparison and export.

Two input modes are retained. In video mode, annotations supply the reference for perception metrics

5.2     Network and Scenario Preparation

5.2.1   Network Provenance and Validation

A selected, manageable Lahore road area will be exported from OpenStreetMap under its applicable
attribution and license conditions [23]. The exact bounding box, extraction date, source file checksum,
and conversion command will be stored. SUMO’s import toolchain will convert the graph, after which
NetEdit inspection will verify lane counts, legal turns, junction types, traffic-light programs, pedestrian-
only edges, disconnected components, and ambulance-accessible routes.

The initial size target from project context is approximately 10–20 signalized intersections, but this
remains a planning range rather than a confirmed network fact. A smaller validated extract is preferable
to a larger inaccurate one. If import quality prevents stable experiments within the schedule, a synthetic
multi-intersection grid with documented geometry and demand becomes the fallback; results will be
identified as synthetic.


5.2.2   Demand and Incidents

Demand files will define light, medium, and heavy conditions plus an uneven approach case. Vehicle
insertion will use explicit random seeds. The warm-up period allows the network to reach a represen-
tative occupancy before measurements. Incident scenarios will close an edge, reduce lane capacity, or
insert a controlled obstruction at a declared simulation time. A failed insertion due to a full lane will be
recorded rather than retried until a favorable run occurs.

The same demand realization will be replayed across controllers where SUMO semantics permit. If a
controller changes route choices or insertion feasibility, the manifest will distinguish the original demand
request from actual departures. Scenario families will be separated into development, tuning, and held-
out evaluation sets.

5.4     Normal Traffic Controllers

5.4.1   Fixed-Time Controller

The fixed controller will use a declared cycle and phase sequence appropriate to the selected junction.
Green, yellow, and all-red durations and offsets will be versioned. It will not be intentionally starved or
given unrealistic timing to make adaptive methods appear superior. A basic saturation check will ensure
that at least the light scenario is serviceable.


5.4.2   Rule-Based Adaptive Controller

The initial transparent controller evaluates only legal candidate phases. A pressure-inspired score for
phase p is
                                 S p (t) =     ∑ (ql (t) − αqm (t)) + β wl (t),                       (5.2)
                                             (l,m)∈p

where ql and qm are upstream and downstream queues for a served movement, wl is the maximum
accumulated wait among its approaches, and α, β are documented configuration values. This follows
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                          39


the motivation of max-pressure control [10] while retaining a direct anti-starvation term.

At each decision instant, the current green is held until minimum green. A phase may be extended if
it remains best and maximum green is not reached. A phase whose maximum red exceeds a limit is
promoted. Switching inserts the same clearance sequence used by all controllers. No controller can
directly bypass the safety filter.


5.4.3   Proposed RL Formulation

One RL formulation will be selected after the rule baseline is stable. A feasible initial choice is a
discrete-action value-based policy for a small, fixed phase set; pressure-informed reward design is sup-
ported by PressLight [12]. If the network needs coordinated agents and the training budget permits,
centralized observations with per-intersection actions are preferred over loosely defined independent
learners.

The proposed state for each decision interval includes normalized incoming and outgoing queues, ap-
proach waiting time, occupancy, current phase, elapsed phase time, and an emergency-mode flag. An
action requests a legal phase or a bounded extension. The safety layer remains authoritative. A candidate
reward is
                                     rt = −λ p Pt − λwWt − λs Xt − λcCt ,                           (5.3)

where Pt is network pressure, Wt normalized waiting, Xt a starvation violation, and Ct an unnecessary-
switch penalty. Coefficients and normalization will be fixed on training/tuning scenarios. Emergency
performance is evaluated in a separate supervisory experiment so that the first normal-controller com-
parison is not confounded by rare mission rewards.

Training will record episode seed, demand profile, exploration schedule, optimizer settings, network
checksum, reward components, and checkpoints. Evaluation uses deterministic policy settings where
applicable and held-out demands. Training return alone is not an evaluation result.

points; edges store length, allowed class, free-flow time, current travel-time estimate, queue discharge
estimate, residual signal delay, closure state, and observation time. The exact representation will match
SUMO route validity rather than an abstract map that permits illegal turns.

5.6    Moving Green Corridor

The corridor operates on a bounded number of route intersections ahead of the ambulance. Activation
may use estimated time to arrival and queue clearance rather than a fixed distance alone. Each inter-
section receives a request containing mission ID, route version, approach movement, predicted arrival,
expiry, and priority level.
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                          41


Before serving the ambulance movement, the coordinator completes minimum green and applies the
configured yellow and all-red clearance for conflicting movements. It does not set every route signal
green at once. Passage is confirmed from the simulated vehicle position and lane transition, with a time-
out as failure detection. After passage, the intersection enters recovery and either completes a bounded
compensation plan or returns at a safe cycle boundary. A revised route cancels obsolete requests. These

5.8.2   Scenario Assignment and Repetition

The evaluation manifest will define demand levels, origin/destination pairs, incident timing, warm-up,
measurement horizon, and repeated seeds before final runs. Every controller receives the same set. The
number of repetitions will be chosen using pilot variance and available computation, then reported rather
than retroactively reduced to favorable cases. Averages will be accompanied by standard deviation or
confidence intervals, and paired differences will be used when runs share a demand seed.

RL training and hyperparameter selection use only training/tuning scenarios. Held-out demand com-
binations and at least one unseen seed set are reserved for final evaluation. Perception data is split by
source or continuous sequence to reduce temporal leakage. The report will include failures, timeouts,
infeasible routes, and safety-filter interventions.

5.8.3       Metric Definitions

For N completed vehicles with travel times Ti , mean travel time is T̄ = N −1 ∑i Ti . Queue length is sam-
pled at fixed simulation intervals and reported as time mean and maximum by approach. Throughput is
the number of vehicles crossing a declared network boundary during the measurement interval. Fairness
includes maximum red time and approach-level delay distribution; an aggregate mean alone can conceal
starvation.

Ambulance delay is actual travel time minus free-flow route time under the same network definition.
Ordinary-traffic impact is evaluated on non-emergency vehicles and includes delay during the mission
plus a recovery interval. Route computation time is measured separately from simulated travel time. For

5.8.4       Reproducibility Package

Each run will retain the source revision, dependency manifest, SUMO version, network and route check-
sums, controller/model version, full configuration, seed, logs, metric schema, and terminal reason. Large
external video and pretrained weights may be referenced by license-aware URI and checksum. A script
should recreate a run from its manifest; any manual NetEdit change must be committed as a network
artifact.



5.9     Threats to Validity

Construct validity is threatened if queue proxies, waiting-time definitions, or reward components do
not represent the intended concept. Definitions and units will be versioned, and perception proxies will
not be renamed as physical quantities without calibration.

Internal validity is threatened by unmatched demand, different warm-up, hidden seed changes, or
controller-specific failures. Paired manifests, one measurement implementation, and retention of failed
runs mitigate these risks.

External validity is limited by synthetic demand, map inaccuracies, simulator car-following assump-
tions, and video domain shift. Findings will be bounded to the tested network, demand families, and
video sources. No clinical response-time or public-road safety conclusion will be drawn.

Conclusion validity is threatened by few repetitions, tuning on the test set, and reporting only means.
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                               45


Pilot variance, held-out scenarios, paired comparisons, variability, and sensitivity analysis will be used.
Statistical tests, if used, will name assumptions and effect sizes; significance alone will not establish
practical value.



5.10     Conclusion

The methodology specifies a feasible progression from validated baselines to integrated emergency con-
trol. It uses time-consistent route costs, hysteresis, explicit corridor transitions, held-out evaluation, and
reproducibility artifacts. Most importantly, it defines how negative or mixed results remain valid findings
rather than prompting undocumented changes to the experiment.

Chapter 6 High-Level and Low-Level Design

This chapter maps the requirements and methodology to a service-oriented prototype design. The de-
composition protects simulation determinism: one adapter owns the simulation clock and all signal actu-
ation, while the API, dashboard, perception, controllers, and experiment store exchange typed messages
without competing for control.



6.1       System Overview and Design Goals

The system must support repeatable research runs, interactive demonstrations, and post-run analysis. Its
principal design goals are: deterministic ownership of state changes; replaceable controller and percep-
tion implementations; explicit time, units, and validity; safe corridor transitions; immutable experimen-
tal configuration; and visible failure. Performance is important only after these properties are preserved.

The design assumes a single machine or small development deployment for Deliverable 2/FYP-I. Sep-
arating components logically does not require premature distribution. In-process modules may be used
initially behind the same interfaces, then isolated as workers if profiling justifies it.

Event ordering is based on simulation step within a run and a monotonic sequence number assigned

6.9    Concurrency, Synchronization, and Resource Ownership

The orchestrator is the only writer to simulation time. TraCI access is serialized behind the adapter.
Controller computation receives an immutable snapshot. Perception uses a bounded work queue; if it
falls behind, the worker marks observations late rather than blocking control. Dashboard streams are
lossy views: a slow client may skip intermediate snapshots but cannot delay decisions.

Run configuration is immutable after start. The current route version is updated atomically with the
cancellation of obsolete corridor requests. Database writes are batched where safe, but an applied signal
event and mission-state transition must not be acknowledged before durable enqueue. On shutdown, the
system stops accepting commands, terminates or detaches SUMO safely, flushes records, and gives the
run an explicit terminal state.

6.11       Detailed Module Policies

6.11.1     Controller Policy

All controllers implement a common method accepting a snapshot, intersection configuration, and de-
cision context, and returning a request plus explanation fields. They cannot write global state or call
TraCI. Deterministic evaluation disables exploration and seeds all permitted stochastic operations. The
safety filter verifies phase membership, minimum green, clearance, maximum priority duration, and
ownership.
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                            55


6.11.2    Routing Policy

The graph builder derives edges from validated SUMO movements. Cost providers are composable but
must state units and whether link time already includes queue delay. A route plan is immutable. The
mission points to one current version, and a revision is accepted only through Algorithm 1. Closures
override cost and invalidate affected routes immediately.


6.11.3    Persistence Policy

The store uses migrations and foreign keys for structured data, and checksummed external artifacts
for large files. Raw high-frequency state may be downsampled for persistence, but the interval and
aggregation method are recorded. Secrets or local filesystem paths are not exported as research data.
Database selection will be confirmed by implementation; the domain schema is independent of that
choice.


6.11.4    User-Interface Policy

Colors are supplemented with labels and icons so congestion or failures are not conveyed by color
alone. Units and source mode appear beside values. Schematic predictions and measured values are
visually distinct. The UI does not display “time saved” until a valid reference run exists under the same
comparison manifest.



6.12      Testing Strategy

Unit tests cover cost functions, route validity, hysteresis, metric calculations, schema validation, and
corridor transition guards. Property or invariant tests generate action sequences to ensure incompatible
greens are never produced and that corridor cancellation eventually reaches IDLE through RECOVERY.
Integration tests run small SUMO networks to validate step ownership, detector-to-state messages, route
application, and persistence. Scenario tests replay fixed seeds for normal control, closure rerouting,
no-route, controller failure, stale data, ambulance timeout, and dashboard disconnect.

Research verification is separate from software correctness. Passing unit tests shows that the implemen-
tation follows its specification; it does not show that the policy improves traffic. Comparative experi-
ments described in Chapter 5 provide that evidence.
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                              56


6.13     Coding, Build, and Maintainability Policies

Python modules will use static type hints, formatting and linting, bounded dependency versions, struc-
tured logging, and docstrings for public interfaces. React components will separate data fetching from
presentation. Configuration is stored as validated files rather than scattered constants. Continuous checks
should run unit tests and a minimal headless SUMO scenario. Releases used for experiments are tagged
and their commit ID is written into run manifests.

The intended repository structure separates application services, controllers, routing, perception, sim-
ulation, dashboard, schemas, scenarios, and experiment artifacts. This is a proposed organization, not
evidence that those directories already exist. Small interfaces allow a tracker, RL algorithm, database,
or dashboard transport to change without rewriting the simulation loop.



6.14     Conclusion

The design assigns one clear owner to every mutable resource and makes source, time, units, route
version, and applied action explicit. The architecture supports the intended progression from baselines to
RL and from static routing to a safe moving corridor, while allowing failures and negative experimental
outcomes to be recorded honestly. It is sufficiently modular for team implementation without requiring
distributed-system complexity at the prototype stage.
