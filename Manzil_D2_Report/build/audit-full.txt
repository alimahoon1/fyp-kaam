Abstract

Manzil is a simulation-based research and development prototype for adaptive urban traffic control and
emergency routing. It combines video-based vehicle detection and tracking, traffic-state estimation,
comparative signal-control policies, congestion-aware ambulance routing, and a moving green corridor
within a SUMO test environment. A React dashboard and FastAPI services are proposed to expose
system state and experimental records. This report specifies the requirements, research method, archi-
tecture, and controlled evaluation protocol; implementation and measured results remain subsequent
project work.
                                                                                                       iii


Executive Summary

Traffic congestion affects daily movement, while delays to an ambulance can carry more serious con-
sequences. Conventional signal plans are prepared for expected demand and cannot respond to every
short-term imbalance. Route guidance based only on distance can also direct an emergency vehicle
toward a road that is short but heavily queued. Manzil addresses these related problems through a con-
trolled research prototype rather than a public-road deployment. It will examine how traffic observations
can support responsive signal decisions, how an ambulance route can reflect current network conditions,
and how selected intersections can provide temporary priority as the vehicle approaches. The expected
value for decision makers is a repeatable environment in which alternative policies can be compared
before any investment in roadside equipment or operational integration is considered. The project does
not promise citywide improvement at this stage. It establishes a practical basis for determining whether
an integrated approach is beneficial, what disruption it causes to ordinary traffic, and which limitations
must be resolved before later field-oriented work could be justified.

The proposed prototype combines recorded-video traffic observation with a simulated urban road net-
work. Recorded video will be used to assess whether vehicle detection and tracking can provide useful
counts and queue-related indicators. SUMO will provide a safe and repeatable setting for comparing
fixed-time, rule-based adaptive, and reinforcement-learning signal control. When an ambulance mission
is created, the system will evaluate valid routes using travel-time and delay estimates rather than dis-
tance alone. A moving green corridor will prepare only the next relevant intersections, allow safe signal
transitions, detect that the ambulance has passed, and return each intersection to normal operation. A
web dashboard will present the current network, selected route, traffic conditions, corridor status, warn-
ings, and experiment summaries. These capabilities are deliberately limited to a manageable prototype
with one active ambulance. Manzil will not connect to government signals, consume live government
CCTV, cover all of Lahore, perform enforcement, or claim the safety certification needed for operational
emergency response.

Project success will be judged through transparent comparisons rather than a visually convincing demon-
stration. Normal-traffic experiments will replay matched demand scenarios and compare waiting time,
queue length, travel time, throughput, and fairness. Emergency experiments will separate the bene-
fit of congestion-aware routing from the additional benefit and disruption of signal priority. Scenario
definitions, seeds, software versions, settings, failures, and metric definitions will be retained so that
outcomes can be reproduced. This report defines the project vision, evidence base, requirements, pro-
posed method, and system design without claiming unperformed results. Implementation choices and
measured targets remain subject to baseline profiling.

Chapter 1 Introduction

Urban traffic control is a networked decision problem. Demand can change by approach, queue spillback
at one junction can obstruct another, and a timing plan that is adequate in one period may waste capacity
in another. Emergency travel adds a stricter timing objective. An ambulance does not benefit merely
from a short geometric path if that path contains slow links, long queues, or signals that repeatedly
stop it. These observations motivate Manzil, a research and development prototype that studies traffic
perception, adaptive signal control, congestion-aware emergency routing, and coordinated signal priority
in one simulation-based environment. Manzil is not presented as a deployable municipal controller. It
is a controlled experimental platform based on the microscopic traffic simulator SUMO and its TraCI
interface [1, 2]. The platform is intended to make policies repeatable, observable, and comparable before
any real-world actuation is considered. Recorded video supplies a second, deliberately bounded input
mode for studying whether vehicle detection and tracking can produce useful traffic indicators. The
simulator remains the authoritative source of network state in routing and signal-control experiments,
which prevents uncertain camera observations from being treated as exact network measurements.



1.1    Purpose of this Document

This Deliverable 2 report translates the approved proposal into a traceable research and software design.
It defines the questions to be investigated, reviews the evidence behind major design choices, specifies
externally visible requirements, and describes the methodology and architecture needed to conduct fair
experiments. It also records the distinction between confirmed project scope, proposed technical choices,
and future implementation work. The report does not claim experimental improvements, real-time per-
formance, model accuracy, or deployment readiness. At the proposal stage, the problem definition, major
functions, and conceptual architecture were established, while dataset preparation, implementation, tun-
ing, and evaluation remained planned work. The methodology therefore defines how later claims must
be produced rather than anticipating their outcome. This distinction is important because a successful
simulation run or a plausible interface design does not demonstrate a measurable improvement. Any
later performance statement must be tied to a recorded configuration, matched baseline, stated metric,
and repeatable set of runs. In this way, the document serves both as the academic basis for assessment
and as an implementation agreement that the team can use to prevent scope drift.

1.2    Intended Audience

The primary audience is the FAST–NUCES FYP supervisor and evaluation panel. They require enough
detail to judge the relevance of the research questions, the feasibility of the proposed software, and the
validity of the evaluation plan. The report is also an engineering reference for the student implementa-
tion team. Team members should be able to derive component responsibilities, interface fields, scenario
configurations, fallback behavior, and planned verification from the chapters that follow. A secondary
audience consists of prospective traffic-management and emergency-service stakeholders who may wish
to understand the problem, operational assumptions, and limits of the prototype. These stakeholders
are not represented as current clients, project partners, or approving authorities. The writing therefore
explains domain terms when they first become important, but it retains the precision needed for imple-
mentation and academic review. Business-level implications are kept separate from technical evidence,
and proposed functions are not described as operational capabilities. This combination allows differ-
ent readers to locate the information relevant to them without weakening the distinction between an
undergraduate research prototype and a real traffic-control system.

Chapter 2 Project Vision

This chapter converts the broad motivation for Manzil into a bounded project vision that can guide both
implementation and evaluation. It identifies the decisions that the prototype is expected to make, the
evidence needed to judge those decisions, and the conditions under which any conclusion must remain
limited to simulation and selected recorded video. The chapter begins with the relationship between
normal traffic control and emergency movement, then states the problem in terms that can be investi-
gated within an undergraduate project. Research questions separate perception quality, normal signal
control, dynamic routing, corridor operation, and robustness so that an improvement in one area is not
mistaken for success in every area. The objectives and scope retain the approved proposal while exclud-
ing forecasting, enforcement, citywide deployment, and direct operation of public signals. Constraints
related to data, map quality, computing resources, and the simulation-to-reality gap are treated as design
inputs rather than footnotes. Stakeholder expectations and success criteria then clarify who can use the
prototype and what evidence would constitute a credible project outcome.



2.1    Problem Domain Overview

Traffic-signal control allocates limited green time among movements that cannot proceed together. Fixed
plans are understandable, auditable, and easy to reproduce, but they cannot respond to every short-term
difference in approach demand. Adaptive control can use measured queues and waiting time, yet a
controller that improves the network average may still be unacceptable if it repeatedly postpones a
lightly loaded approach. Coordination adds another layer because an action at one intersection changes
arrivals and queues downstream. Emergency routing operates on the same network with a stricter travel-
time objective. A route is useful only when its cost reflects current link travel time, queue discharge,
signal delay, and any closure that makes a movement unavailable. Signal priority may reduce ambulance
stops, but an unsafe transition or poorly managed recovery can transfer excessive delay to ordinary
traffic. Manzil therefore treats normal control, route selection, priority activation, passage detection, and
recovery as connected decisions. It retains separate measures for the ambulance and other vehicles so
that emergency benefit cannot conceal network disruption.

2.2    Problem Statement

Within the selected prototype setting, there is no established implementation that allows the Manzil team
to compare signal-control strategies and isolate the contributions of emergency routing and coordinated
priority under one reproducible protocol. The project problem is therefore to design a system that
observes or simulates traffic state, makes bounded control and routing decisions, and records why each
decision was requested and what was actually applied. The system must support matched comparisons
between fixed-time, rule-based adaptive, and reinforcement-learning control under the same demand
CHAPTER 2. PROJECT VISION                                                                               9


conditions. It must also compare an unassisted ambulance, congestion-aware routing, and routing with a
moving corridor without changing unrelated configuration between runs. This requires more than joining
familiar technologies. Measurements must have defined units and freshness, routes must remain legal
from the current vehicle position, signal changes must respect phase safety, and failed or infeasible runs
must remain visible. The resulting evidence will describe performance in declared simulation and video
conditions. It will not establish that the same effect would occur on public roads without calibration,
controller integration, safety engineering, authority approval, and field validation.



2.3    Problem Elaboration

Five linked sub-problems determine whether the prototype can answer its research questions. First,
frame-level vehicle detections must be associated over time and assigned to meaningful road regions be-
fore they can support counts, trajectories, or queue-related observations. Second, normal signal control
requires a correctly configured fixed baseline and a transparent adaptive baseline before reinforcement
learning can be judged fairly. Third, route costs must use compatible units and avoid adding separate
congestion penalties when observed travel time already contains the same delay. Fourth, corridor con-
trol must anticipate the ambulance, clear conflicting movements, limit the duration of priority, detect
passage, and restore normal service without holding the entire route green. Fifth, experiments must use
matched demand, seeds, warm-up, duration, and metric definitions. These issues also interact across
component boundaries. A stale observation can change an edge cost, a route revision can invalidate
pending priority, and a prolonged priority phase can improve ambulance time while harming ordinary
traffic. The vision consequently requires explicit freshness, single ownership of simulation time and
actuation, safe fallback, route versioning, and auditable event order.

RQ4        Holding routing logic constant, what additional emergency benefit and ordinary-traffic dis-

RQ5        How sensitive are the conclusions to demand level, incident placement, random seed, and

The research questions deliberately avoid the vague claim that Manzil will create “better traffic.” Each
question controls a specific factor and identifies evidence that can support or reject the corresponding
claim. RQ1 concerns the reliability of observable video measurements and is judged against held-out
annotations. RQ2 compares normal controllers under matched SUMO scenarios and includes fairness so
that a lower network mean cannot hide starvation. RQ3 holds signal behavior constant while changing
the route policy, which isolates the value of dynamic congestion information. RQ4 then holds routing
logic constant while enabling the corridor, allowing its additional emergency benefit and its cost to
ordinary traffic to be measured. RQ5 tests whether conclusions persist when demand, incidents, random
seeds, or observation quality change. This separation also defines the order of implementation. The
team can complete and validate fixed and rule-based control before training an RL policy, and it can
validate route legality before adding priority. If one question cannot be answered within the available
evidence, the remaining comparisons can still produce defensible findings without inventing an overall
success claim.

2.7    Sustainable Development Goals

Manzil aligns principally with United Nations Sustainable Development Goal 11, which concerns in-
clusive, safe, resilient, and sustainable cities [4]. The relevant connection is the investigation of how
existing road and signal capacity might be used more responsively under changing traffic conditions,
together with a structured method for prioritizing an emergency journey. The prototype can provide
evidence about simulated waiting time, queue formation, throughput, ambulance travel time, and the re-
covery of ordinary traffic after priority. These measures are appropriate for a computing project because
they can be defined and reproduced within the selected environment. The alignment must nevertheless
be stated cautiously. A SUMO experiment does not demonstrate city-level sustainability, reduce emis-
sions directly, or establish a public-health outcome. The project also does not model patient condition,
clinical triage, hospital capacity, or the relationship between travel time and survival. Its secondary
relevance to health is limited to studying a transport mechanism that may reduce simulated ambulance
delay. Any stronger claim would require operational traffic data, emergency-service participation, field
trials, and outcome measures outside the approved scope.



2.8    Constraints and Assumptions

The main constraints are the semester-scale implementation period, limited access to calibrated local
traffic data, camera perspective and occlusion, finite model-training hardware, and the gap between sim-
ulated and real driving behavior. These constraints require a network small enough for repeated runs and
detailed validation. A recognizable urban extract is preferred, but a documented synthetic grid remains
an acceptable fallback if imported lane connections or signal programs cannot be corrected reliably
within the schedule. The core experiments assume one active ambulance, valid origin and destination
edges, controlled traffic generation, and no direct actuation of public infrastructure. Video-derived queue
length remains an observable proxy unless the camera is calibrated to physical road geometry. The ex-
act tracker, reinforcement-learning algorithm, database engine, hardware, map size, timing thresholds,
and training budget are proposed choices rather than confirmed facts. These assumptions will be stored
with experiment configurations because they affect interpretation. When an assumption fails, the sys-
tem must report the failure or use a declared fallback instead of silently changing the scenario. This
treatment makes constraints part of the research design and prevents later results from appearing more
general than the tested conditions support.

2.9     Business and Practical Opportunity

The practical opportunity for Manzil is an experimentation and decision-support environment rather than
an immediately deployable traffic product. A repeatable simulator can help a technical team compare
how signal policies react to balanced, uneven, congested, and incident-affected demand. It can also
show a prospective traffic or emergency-service stakeholder why the fastest ambulance route may differ
from the shortest route, how a moving corridor progresses, and how much ordinary traffic is disrupted
during and after priority. The dashboard and stored run manifests make those decisions visible instead of
presenting the controller as a black box. This capability could support later feasibility studies, training
demonstrations, or policy prototyping if the research results justify continued work. A commercial or
public-sector deployment would require substantially more evidence: calibrated local demand, validated
sensing, compatible roadside controllers, resilient communications, cybersecurity controls, privacy re-
view, safety assurance, authority approval, and field trials. The current project assumes none of these
partnerships or approvals and makes no revenue claim. Its immediate value lies in producing a defensible
prototype and evaluation method that can reveal both benefits and limitations.

2.11     Success Criteria

Success is not defined by a visually impressive ambulance moving through green signals. The proto-
type must first behave correctly: scenario inputs must be validated, only one component may advance
SUMO, signal transitions must remain legal, routes must follow permitted movements, obsolete corri-
dor requests must be cancelled after rerouting, and failures must be recorded visibly. Research success
then depends on comparison quality. Controllers must receive matched demand and seeds, emergency
modes must differ only in the factor being tested, and metrics must retain the same definition across
runs. Results should report variability rather than selecting a single favorable trace. A perception con-
clusion must refer to held-out annotations and the stated camera conditions, while a control conclusion
must refer to the named network, demand family, run duration, and simulator configuration. Mixed or
negative results remain valid if the protocol is followed. A method that improves ambulance time while
causing unacceptable normal-traffic delay, starvation, unsafe transitions, or unstable rerouting cannot be
described as successful overall. These criteria give the team concrete acceptance conditions and provide
evaluators with a basis for judging both technical correctness and academic rigor.

Chapter 3 Literature Review and Related Work

This chapter examines the research needed to justify Manzil’s design rather than treating the use of fa-
miliar tools as a contribution. The review is organized around five decisions: how traffic is observed,
how normal signals are controlled, how learned policies are evaluated, how emergency routes are se-
lected, and how signal priority is activated and recovered. Each study is considered in its original data or
simulation setting because reported values from incompatible benchmarks cannot be treated as a com-
mon comparison. The discussion identifies the method, evidence, limitations, and direct implication for
a Manzil design choice. Research papers are distinguished from official software documentation, which
is used to establish interface capabilities but is not counted toward the study requirement. The purpose
is not to assemble every publication on intelligent transportation. It is to establish whether the proposed
components are technically defensible, which assumptions must be recorded, and where a controlled
undergraduate experiment can add useful evidence. The final synthesis consequently states a precise
integration question instead of claiming that the use of YOLO, reinforcement learning, or shortest-path
search is itself novel.



3.1     Review Method and Terminology

The approved proposal supplied the initial bibliography, after which each retained study was checked
against a publisher page, proceedings record, DOI, or official open-access paper. Selection required
direct relevance to vehicle detection and tracking, traffic-state estimation, signal control, simulation,
graph routing, or emergency preemption. The review also applies consistent terminology. Detection
refers to locating and classifying vehicles within one frame, while tracking refers to associating those
observations through time. A detector therefore cannot produce reliable passage counts by itself. Signal
priority describes preferential treatment that may remain within normal timing constraints, whereas
preemption may interrupt normal operation for an emergency request. Manzil uses the term moving
green corridor for a coordinated sequence of bounded interventions ahead of the ambulance, not for a
permanently green route. These distinctions affect the interpretation of prior results and the design of the
proposed experiment. A paper reporting benchmark detection accuracy does not establish a calibrated
queue estimate, and a study of isolated preemption does not automatically validate network-level routing.
The following sections preserve those boundaries when relating the literature to Manzil.

3.2     Vision-Based Traffic Observation

3.2.1   One-Stage Object Detection

Redmon et al. formulated YOLO as a single network that predicts bounding boxes and class probabil-
ities from an image in one evaluation [5]. The study established the feasibility of real-time one-stage
detection and reported a strong speed advantage, while also identifying localization error as a relative
weakness. The design is relevant to Manzil because a compact inference path is practical for recorded
traffic video and may later support a live demonstration on available hardware. The evidence does not
establish accuracy for every vehicle class, road layout, camera height, weather condition, or Lahore
traffic scene. A selected pretrained checkpoint must therefore be evaluated on the project’s own held-
out sequences, and confidence or intersection-over-union thresholds cannot be copied from an unrelated
benchmark. Frame-level boxes also do not provide stable counts by themselves. The same vehicle may
be detected in many frames, an occluded vehicle may disappear temporarily, and perspective changes
apparent size across the image. Manzil consequently treats one-stage detection as the first part of a
measurement pipeline that also requires tracking, road-region assignment, temporal aggregation, and
explicit uncertainty.


3.2.2   Multi-Object Association

Wojke et al. extended a simple online tracker with a learned appearance metric to improve associa-
tion through longer occlusions [6]. Appearance information can reduce identity switches, but it adds
a feature-extraction model, processing cost, and sensitivity to domain differences. ByteTrack follows
a different strategy by associating high-confidence detections first and then attempting to recover true
objects from lower-confidence boxes rather than discarding them [7]. The authors evaluated it across
several tracking benchmarks and reported strong accuracy with real-time throughput on their stated hard-
ware. This approach is relevant to traffic video because occlusion and motion blur often reduce detection
confidence. Neither benchmark establishes Manzil’s processing speed, lane assignment, or queue accu-
racy. An identity-preserving track still requires a road-contact point, direction rule, and region geometry
before it becomes a valid traffic observation. These studies therefore motivate an empirical tracker
choice based on held-out count error, identity stability where identities are needed, failure under oc-
clusion, and end-to-end throughput on the team’s hardware. If a simpler association method produces
equally reliable aggregate counts, its lower complexity may be preferable.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                            18


3.2.3   Traffic Datasets and Domain Coverage

BDD100K provides a large and diverse driving dataset with detection, tracking, and other driving-
scene annotations collected across varied locations, weather, and times [8]. Its diversity is useful for
model initialization and stress testing, although its primarily vehicle-mounted viewpoint differs from a
fixed roadside or elevated camera. UA-DETRAC focuses directly on vehicle detection and tracking in
traffic-surveillance video, making its camera geometry and evaluation protocol closer to an intersection-
observation task [9]. Its scenes still cannot be assumed to represent Lahore traffic composition, mo-
torcycle and rickshaw prevalence, lane discipline, lighting, or camera placement. The two datasets
are therefore complementary references rather than automatic substitutes for local validation. Manzil
should use licensed public sequences where they support reproducible evaluation and may add a small,
separately documented local sample if collection permission and annotation effort are feasible. These
datasets also influence the split strategy. Adjacent video frames are highly correlated, so a random frame
split can place nearly identical observations in training and test data. The project will split by source or
continuous sequence, retain a held-out evaluation set, and avoid tuning thresholds on that set.



3.3     Conventional and Adaptive Signal Control

3.3.1   Fixed-Time Baseline

A fixed-time controller remains necessary even when it is not expected to dominate every scenario. It
provides a stable reference against which the value of traffic-responsive decisions can be measured, and it
helps reveal whether demand generation or metric collection is biased before more complex controllers
are introduced. The baseline must be credible rather than deliberately weak. Manzil will therefore
document its phase sequence, green times, yellow and all-red clearance, cycle length, offsets where
relevant, minimum service, and the demand conditions used to choose those settings. The same phase
definitions and safety transitions will be shared with adaptive controllers so that a comparison does
not reward one controller for using an illegal or more permissive movement set. Fixed timing is also
useful for route and corridor ablations because its behavior is deterministic and easy to reproduce. If
the fixed plan is severely under-saturated or over-saturated in every scenario, differences in controller
performance will be difficult to interpret. A basic capacity and queue check will therefore confirm that
the scenario family contains meaningful light, medium, and heavy conditions instead of a single demand
level chosen to favor adaptation.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                            19


3.3.2   Max-Pressure Control

Varaiya formalized max-pressure control for a network of signalized intersections using differences be-
tween upstream and downstream queue conditions [10]. Selecting a phase that reduces network pressure
has a clearer transportation basis than combining arbitrary percentages without explaining what the score
represents. The approach is responsive and can operate from local movement information, which makes
it a valuable non-learning reference for Manzil. Its assumptions still matter. Queue observations must
correspond to valid movements, downstream storage must be represented, and a theoretical selection
rule does not remove practical minimum-green, yellow, all-red, or maximum-red constraints. Manzil’s
initial rule-based adaptive controller will therefore use a pressure-inspired score only when the required
upstream and downstream measures are available and sufficiently fresh. Waiting time or maximum-red
information will remain as an explicit fairness safeguard so that a low-volume approach is not postponed
indefinitely. The controller will also provide a reason for each request, allowing reviewers to see which
queues and constraints influenced the decision. This transparency makes the baseline useful even if the
later reinforcement-learning policy does not outperform it.



3.4     Reinforcement Learning for Traffic Signals

3.4.1   Cycle-Level Deep Q-Learning

Liang et al. used deep reinforcement learning to adjust traffic-light cycle behavior from observed traffic
state [11]. The study demonstrates how an action definition, decision interval, state representation, and
reward can be joined into a trainable signal controller. It also illustrates a limitation common to traffic
RL: performance obtained for a particular intersection, simulator configuration, demand pattern, and
training budget cannot be assumed to transfer to a different network. Manzil will therefore not reproduce
a reported improvement as an expected project target or select deep Q-learning merely because it is
familiar. A value-based method is feasible only after the discrete action space is bounded, legal phase
transitions are enforced outside the learned policy, and fixed and rule-based baselines behave correctly.
State normalization and reward components must be declared before evaluation, while training and
tuning scenarios must remain separate from held-out tests. The policy will be assessed using traffic
measures and safety interventions, not training return alone. If a simpler controller performs as well
under the selected scenarios, that result will be reported rather than interpreted as a failure to produce a
sufficiently complex model.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                          20


3.4.2   Pressure-Informed Reward Design

PressLight connects reinforcement-learning state and reward design to the transportation concept of max
pressure [12]. The paper argues that a theoretically grounded pressure signal can reduce reliance on ar-
bitrary handcrafted objectives and evaluates the method against conventional and learning baselines in
arterial networks. This is relevant to Manzil because a reward based only on total waiting time may con-
ceal spillback, unbalanced approaches, or repeated postponement of a minor movement. Pressure can
provide a principal network-efficiency signal, while explicit penalties or constraints can address starva-
tion and unnecessary switching. The study does not remove the need for careful evaluation. Topology,
movement mapping, flows, phase definitions, observation range, and training budget all influence the
learned result. Manzil must therefore record the exact state features, normalization, action timing, re-
ward components, and safety interventions used by the selected policy. Emergency priority will initially
remain a supervisory state machine rather than a rare reward event folded into normal training. That sep-
aration permits the normal-controller comparison to be interpreted independently and lets the additional
effect of the corridor be measured through a controlled ablation.


3.4.3   Phase Competition and Network Cooperation

FRAP represents competition among signal phases and exploits structural relationships so that equiva-
lent movements need not be learned as unrelated cases [13]. This is useful where an intersection contains
several competing phases, but it requires an accurate phase graph and a more specialized representa-
tion. CoLight addresses cooperation across intersections through graph attention, allowing neighboring
conditions to influence an agent’s decision [14]. Chu et al. similarly study decentralized multi-agent
deep reinforcement learning at larger scale and emphasize the importance of communication and par-
tial observability [15]. Together, these studies show why the phrase “multi-intersection RL” is not a
complete method. A project must state whether one centralized policy chooses all actions, independent
agents operate without communication, or cooperating agents exchange defined observations. Multi-
agent learning also introduces non-stationarity because each agent experiences an environment affected
by policies that are changing at the same time. For Manzil, attention-based coordination may exceed
the available tuning budget and make attribution difficult. The initial design will therefore use a small
network and one explicit ownership model, adopting useful phase-structure ideas without claiming to
reproduce every cited architecture.

3.4.4   Simulation Environments

CityFlow was introduced as a reinforcement-learning environment designed for large-scale city traffic
and high simulation throughput [16]. It is an important alternative when training speed and very large
networks dominate the design. SUMO is retained for Manzil because the approved proposal already de-
pends on its microscopic vehicle model, traffic-light programs, OpenStreetMap conversion tools, NetE-
dit workflow, and TraCI interface. Lopez et al. describe the simulator’s architecture and its support
for detailed, externally controlled experiments [1]. This combination is appropriate for a manageable
multi-intersection prototype in which route validity, individual ambulance movement, signal transitions,
and per-vehicle outcomes must be inspected. Retaining SUMO also avoids the additional work of show-
ing that a migrated network and demand model behave equivalently in another simulator. The choice
does not make simulation results equivalent to field evidence. Car-following parameters, lane connec-
tions, signal programs, vehicle insertion, and map cleanup can materially change outcomes. Manzil will
therefore version the network, demand, routes, simulator settings, and software release, and it will limit
conclusions to the declared simulation conditions.



3.5     Dynamic Routing

Dijkstra’s algorithm finds a minimum-cost path on a graph whose edge weights are nonnegative [17].
Hart, Nilsson, and Raphael established the formal basis of A*, which adds a heuristic lower-bound es-
timate to guide the search [3]. Both methods are well established, so selecting either algorithm is not
a research contribution by itself. Manzil’s project-specific task is to build a graph that respects valid
SUMO vehicle movements and to define a cost that reflects time rather than distance alone. The pro-
posed cost combines link travel time with non-overlapping estimates of queue discharge and residual
signal delay, all expressed in seconds. If measured link travel time already includes queue delay, a sepa-
rate congestion term cannot be added without double-counting. Dijkstra will provide the reference route,
while A* is permitted only when free-flow travel time forms an admissible lower bound under nonneg-
ative added delay. Dynamic rerouting also needs stability. A route will change when the current path
becomes infeasible or when an alternative offers a persistent improvement above a defined threshold.
Route revisions, no-route cases, and computation time will be evaluated rather than treated as incidental
log messages.
CHAPTER 3. LITERATURE REVIEW AND RELATED WORK                                                            22


3.6    Emergency Routing and Signal Preemption

Humagain et al. systematically reviewed emergency-vehicle route optimization and preemption methods
and identified recurring concerns involving dynamic traffic data, travel-time objectives, ordinary-traffic
effects, safety, and limited real-world application [18]. The review supports an integrated evaluation
but does not justify the unsupported claim that integrated solutions do not exist. Qin and Khan exam-
ine transitions into emergency preemption and recovery to normal timing, including clearance and the
queues created by interruption [19]. Their work shows that preemption is a lifecycle rather than a single
instruction to set an approach green. Louati et al. investigate queue-aware emergency crossing across
signalized intersections [20]. This is relevant because a green signal does not guarantee an unobstructed
approach when the standing queue cannot discharge before the emergency vehicle arrives. Manzil there-
fore models requested, safe-transition, active-priority, passage, recovery, and cancellation states. It also
uses look-ahead activation, timeout, downstream checks, and bounded priority duration. The precise
timing values remain configurable simulation policies, not certified real-world safety parameters, and
the evaluation will report ordinary-traffic disruption together with ambulance benefit.



3.7    Synthesis and Research Gap

The literature establishes reliable building blocks while exposing the risks that arise when they are
connected. One-stage detection is fast enough to investigate traffic video, but useful traffic indicators
require tracking, road geometry, temporal rules, and validation on the intended viewpoint. Max-pressure
and reinforcement-learning research provide responsive control strategies, yet their comparison depends
on state representation, phase constraints, reward design, training data, and simulator configuration.
Dijkstra and A* solve well-defined path problems, but emergency routing remains only as credible
as its movement graph, time-based costs, observation freshness, and rerouting stability. Preemption
research makes safe transition and recovery central, and the review of emergency methods shows why
ordinary-traffic disruption cannot be omitted. Manzil’s proposed contribution is consequently not a new
detector, shortest-path algorithm, or reinforcement-learning family. It is the controlled evaluation of an
integrated and traceable prototype in which perception and simulation evidence remain distinct, normal
controllers receive matched scenarios, routing and corridor effects are separated, and ambulance benefit
is reported with network disruption and recovery. The unresolved question is whether that integration
yields consistent benefits under the selected scenarios and constraints.

3.8    Conclusion

The review supports a conservative technical strategy in which evidence is built in stages. Transparent
fixed-time and pressure-inspired controllers must operate correctly before a learned controller is com-
pared with them, and measurement definitions must be fixed before any optimization result is interpreted.
Video experiments should assess the complete observation chain rather than quote detector accuracy as
a traffic-management result. Simulation experiments should use matched seeds, identical safety con-
straints, and held-out scenarios so that controller differences are not confused with different demand.
Emergency evaluation must also separate the effect of route selection from the effect of signal priority,
because combining both changes in one comparison would prevent a clear explanation of any improve-
ment. The cited literature justifies the selected building blocks but does not establish their performance
for Manzil’s network, cameras, or computing resources. Chapter 4 therefore converts these findings into
traceable requirements, while Chapter 5 defines the measurements and controlled comparisons needed
to answer the research questions without claiming field deployment or certified safety evidence.

Chapter 4 Software Requirement Specifications

This chapter translates the reviewed problem and evidence into a specification for the Manzil research
prototype. The requirements describe observable behavior rather than implying that every item has al-
ready been implemented. Where the available repository evidence does not support a measured thresh-
old, the text states a design target or requires profiling before a value is fixed. The specification gives
particular attention to reproducibility, legal signal transitions, observation freshness, route-version con-
sistency, and visible failure handling because these properties determine whether later experiments can
be interpreted. It also separates the video-perception workflow from SUMO-based control experiments
so that estimated observations are not silently presented as simulator ground truth. Account manage-
ment, public dispatch integration, traffic enforcement, clinical response prediction, and physical signal
deployment remain outside the approved scope. The resulting requirements provide a contract for the
architecture in Chapter 6 and a traceable basis for the evaluation procedures in Chapter 5.



4.1    System Features

The prototype is organized into six feature groups that follow the operator’s experimental workflow
from configuration to evidence export. The grouping prevents a user-interface screen or implementation
library from being mistaken for a requirement and clarifies which service owns each outcome. It also
shows that emergency operation is not an isolated routing feature: a valid mission depends on scenario
state, traffic observations, signal control, monitoring, and durable records. The following statements
summarize those groups before the individual functional requirements define testable behavior.

   1. The operator can select a network, demand profile, controller, seed, incident, duration, and op-
      tional emergency mission before a run begins.

   2. The perception workflow can process licensed recorded video into detections, tracks, road-region
      observations, and timestamped aggregate measures with confidence information.

   3. The simulation workflow advances SUMO through one owner, reads traffic state, applies fixed or
      adaptive requests, and preserves legal phase transitions.

   4. The emergency workflow validates endpoints, computes a dynamic path, applies stable rerouting,
      activates bounded moving priority, detects passage, and recovers normal control.

   5. The monitoring interface presents map state, signals, traffic indicators, ambulance route, corridor
      state, warnings, and the current data-source mode.

   6. The experiment service retains immutable configuration, events, metrics, software versions, seeds,
CHAPTER 4. SOFTWARE REQUIREMENT SPECIFICATIONS                                                           27


       and termination state for comparison and export.

4.4    Assumptions and Dependencies

SUMO and TraCI are required for controlled traffic experiments [1, 2]. A selected network must contain
legal lane connections and signal plans after import and manual cleanup, and representative routes must
be validated before it is used for comparison. Video sources require sufficient visibility, a documented
license or team authorization, and annotations appropriate to the selected measure. The simulation as-
sumes one clock owner, nonnegative route costs, and emergency endpoints on ambulance-accessible
edges. It also assumes that configured phase transitions reflect the validated simulation network; they
are not certified timings for physical signal hardware. The dashboard is an operator and evaluator tool
rather than an autonomous public dispatch system, and a displayed route does not constitute operational
navigation advice. When an assumption cannot be met, the affected workflow must stop or disclose a
bounded fallback. It must not silently substitute a different network, data source, time unit, or observa-
tion mode because that would make later comparisons irreproducible.

React and FastAPI are fixed by the approved proposal for the interface and application service boundary
[21, 22]. Python is implied by the planned perception, reinforcement-learning, and TraCI ecosystem.
PostgreSQL, a WebSocket transport, Docker, and specific chart or map libraries are proposed dependen-
cies and remain replaceable until implementation confirms them. These assumptions are deliberately
narrower than a production deployment specification. Manzil is evaluated as a controlled prototype on
prepared networks, not as an interface to public signal controllers or ambulance dispatch infrastruc-
CHAPTER 4. SOFTWARE REQUIREMENT SPECIFICATIONS                                                         31


ture. A selected video source must have suitable permission and sufficient visibility for the intended
annotation task, while the simulation network must be checked for lane connectivity, valid traffic-light
programs, and ambulance-accessible routes. If any assumption fails, the run must be rejected or marked
with an explicit limitation instead of substituting an undocumented configuration. This treatment keeps
dependencies traceable and prevents a convenient library choice from becoming an unsupported archi-
tectural claim.

4.11     Conclusion

The specification centers on traceability and failure visibility rather than on a collection of loosely con-
nected features. It requires one simulation-clock owner, legal signal transitions, stable route revision,
explicit observation freshness, immutable run configuration, and comparisons that cannot hide incom-
patible settings or failed trials. Functional requirements define what the operator and services must
observe, while non-functional requirements constrain timing, ownership, privacy, auditability, and re-
covery. The use cases exercise both successful and failed paths, the wireframes show how critical state
and provenance remain visible, and the data model preserves the route and decision history needed for
later analysis. Risks and traceability link those requirements to bounded fallbacks and planned verifi-

Chapter 5 Proposed Approach and Methodology

This chapter defines how Manzil will be constructed and evaluated so that the research questions can
be answered with controlled evidence rather than a favorable demonstration run. The method begins
by freezing definitions, exclusions, baselines, and data partitions before the final comparison. It then
validates the network, observations, controllers, routing, and corridor lifecycle in stages, because a re-
sult from an integrated run is not interpretable when an underlying measurement or safety transition is
still uncertain. Figure 5.1 summarizes this sequence from preparation to reporting. Each stage produces
an artifact or acceptance check that is retained with the experiment manifest. The protocol also sep-
arates detector evaluation from signal-control evaluation: recorded video supplies annotated evidence
for perception, while SUMO supplies controlled vehicle and signal state for the controller, route, and
emergency experiments. This separation prevents estimated video quantities from being passed off as
exact network state and allows an optional observation-noise study only after both baselines are stable.

The workflow in Figure 5.1 is ordered to prevent later components from masking earlier faults. Research
questions and metric definitions are fixed before data preparation; the network and demand are validated
before controllers are compared; and ordinary traffic control is established before emergency routing and
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                             46


priority are enabled. Two input modes are retained throughout this process. In video mode, annotations
provide the reference for perception metrics, and no claim is made that a selected clip determines the full
state of the simulated network. In simulation mode, SUMO supplies lane, vehicle, signal, and route state
for controlled experiments. Both modes use the same typed traffic-state concepts but retain a source field,
units, validity interval, and confidence where applicable. A later noise experiment may inject measured
perception error into simulation observations, but it will be included only after the baseline protocol is
complete and its parameters are fixed in advance. The final stage reports variability, failures, ablations,
and validity limits alongside successful runs.



5.2      Network and Scenario Preparation

5.2.1    Network Provenance and Validation

A selected, manageable Lahore road area will be exported from OpenStreetMap under its applicable
attribution and license conditions [23]. The exact bounding box, extraction date, source file checksum,
and conversion command will be stored so that a later change in the public map cannot silently alter an
experiment. SUMO’s import toolchain will convert the graph, after which NetEdit inspection will verify
lane counts, legal turns, junction types, traffic-light programs, pedestrian-only edges, disconnected com-
ponents, and ambulance-accessible routes. Automated checks will then attempt representative routes,
enumerate signal phases, and reject movements that conflict with the intended vehicle classes. The ini-
tial planning range is approximately 10–20 signalized intersections, but this is not a confirmed network
fact or a requirement to retain a defective import. A smaller validated extract is preferable to a larger
inaccurate one because route continuity and lawful signal control are prerequisites for every later result.
If the chosen map cannot be stabilized within the schedule, a documented synthetic multi-intersection
grid becomes the fallback, and all results will be identified as synthetic rather than generalized to Lahore
roads.


5.2.2    Demand and Incidents

Demand files will define light, medium, and heavy conditions together with an uneven-approach case
that can expose starvation. Vehicle insertion uses explicit random seeds, and a declared warm-up inter-
val allows traffic to populate the network before measurement begins. Incident scenarios close an edge,
reduce lane capacity, or introduce a controlled obstruction at a fixed simulation time. A failed inser-
tion caused by a full lane is retained as an outcome rather than retried until the run appears favorable.
The same requested demand and seed are replayed across controllers where SUMO semantics permit.
When controller behavior changes route choice or insertion feasibility, the manifest distinguishes the
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                                   47


original demand request from actual departures so that throughput is not interpreted without its denomi-
nator. Scenario families are separated into development, tuning, and held-out evaluation sets before final
runs. Origin-destination pairs, incident timing, and emergency dispatch time are also matched within
each comparison. These controls make differences attributable to the selected policy while preserving
congestion effects that legitimately arise from that policy.

5.4     Normal Traffic Controllers

5.4.1   Fixed-Time Controller

The fixed controller will use a declared cycle and phase sequence appropriate to each selected junction.
Green, yellow, all-red, cycle, and offset values will be versioned with the scenario, and the same move-
ment definitions and clearance rules will constrain every competing controller. The baseline will not
be intentionally starved or assigned unrealistic timing to make adaptation appear superior. Initial green
splits will be selected from the declared demand and checked against approximate approach service so
that at least the light scenario is feasible and heavier scenarios create interpretable congestion rather than
immediate gridlock. Its deterministic schedule makes it useful for validating demand generation, metric
collection, ambulance route ablations, and replay before learning is introduced. If a run violates phase
invariants or produces implausible counts under fixed control, adaptive and reinforcement-learning com-
parisons are postponed until the cause is resolved. The baseline therefore serves as both a comparator
and a diagnostic reference, not as a weak opponent constructed for a favorable result.


5.4.2   Rule-Based Adaptive Controller

The initial transparent controller evaluates only legal candidate phases. A pressure-inspired score for
phase p is
                                 S p (t) =     ∑ (ql (t) − αqm (t)) + β wl (t),                         (5.2)
                                             (l,m)∈p

where ql and qm are upstream and downstream queues for a served movement, wl is the maximum
accumulated wait among its approaches, and α, β are documented configuration values. This follows
the motivation of max-pressure control [10] while retaining a direct anti-starvation term.

Equation 5.2 assigns a transparent score to each legal candidate phase using upstream demand, down-

stream congestion, and the longest accumulated approach wait. The downstream term discourages serv-
ing a movement whose receiving link lacks space, while the wait term provides a direct safeguard against
repeatedly postponing a low-volume approach. Coefficients are configuration values established on de-
velopment scenarios and retained with the run manifest. At each decision instant, the current green is
held until minimum green has elapsed. It may then be extended when it remains the preferred phase and
maximum green has not been reached. A phase whose maximum-red limit is approached receives ex-
plicit promotion, and every switch inserts the same yellow and all-red sequence used by other controllers.
The controller returns a requested phase and its contributing values; it does not actuate SUMO directly.
This explanation record permits a reviewer to distinguish an algorithmic request from a safety-filter
transformation and to diagnose whether observed performance came from pressure, fairness promotion,
or repeated intervention.


5.4.3   Proposed RL Formulation

One reinforcement-learning formulation will be selected only after the fixed and rule-based baselines
are stable. A feasible initial choice is a discrete-action value-based policy for a small, fixed phase set;
pressure-informed reward design is supported by PressLight [12]. The action space requests one legal
phase or a bounded extension, while the safety layer retains authority over minimum green and clearance.
If the chosen network requires coordination and the training budget permits it, centralized observations
with per-intersection actions are preferable to loosely defined independent learners because ownership
and shared information remain explicit. Model architecture, observation normalization, replay settings,
exploration schedule, optimizer, training budget, and checkpoint-selection rule will be recorded before
held-out evaluation. This design does not assume that reinforcement learning will outperform the trans-
parent baseline. If it fails to converge, violates fairness constraints, or offers no consistent held-out
benefit, that outcome remains part of the research evidence and the working rule-based controller re-
mains the operational fallback.

The proposed state for each decision interval includes normalized incoming and outgoing queues, ap-
proach waiting time, occupancy, current phase, elapsed phase time, and an emergency-mode flag. An
action requests a legal phase or a bounded extension. The safety layer remains authoritative. A candidate
reward is
                                    rt = −λ p Pt − λwWt − λs Xt − λcCt ,                              (5.3)

switch penalty. Coefficients and normalization will be fixed on training/tuning scenarios. Emergency
performance is evaluated in a separate supervisory experiment so that the first normal-controller com-

parison is not confounded by rare mission rewards.

Equation 5.3 combines network pressure, normalized waiting, starvation violations, and unnecessary

Training records episode seed, demand profile, exploration schedule, optimizer settings, network check-

declared tuning criterion rather than the best result on the final scenarios. Evaluation uses deterministic
policy settings where applicable and the same safety filter, demand manifests, warm-up, and measure-

depends on reward scaling and does not directly establish travel time, fairness, or safety. Emergency

improves average delay but produces unacceptable maximum-red behavior.



5.5    Dynamic Graph Routing

The routing graph represents legal vehicle movements rather than only geometric road adjacency. Nodes
may be junctions or lane and edge transition points, while edges retain length, allowed vehicle class,
free-flow time, current travel-time estimate, queue-discharge estimate, residual signal delay, closure
state, and observation time. The exact representation must reproduce SUMO route validity, including
turn restrictions and internal connections, so that an algorithm cannot return a visually plausible but
undrivable path. Every cost field states its unit and source, and stale observations are rejected or replaced
by a declared fallback estimate. Equation 5.4 expresses the primary cost in seconds. Link travel time,
signal delay, and queue delay are separated only when their estimators do not overlap; if a measured link
time already contains queuing, another queue penalty would double-count congestion. A hard closure
receives infinite cost, while temporary slowdowns retain finite nonnegative estimates. The complete cost
snapshot is versioned with any accepted route so that a later evaluator can reconstruct why it changed.

5.6    Moving Green Corridor

The moving corridor operates on a bounded number of intersections ahead of the simulated ambulance
instead of setting an entire route green. Activation considers estimated arrival, standing queue clearance,
signal state, and downstream capacity rather than distance alone. Each request identifies the mission, im-
mutable route version, approach movement, predicted arrival, expiry, and priority level. Before serving
that movement, the coordinator completes the active phase’s minimum service and applies the config-
ured yellow and all-red clearance to conflicting movements. Passage is confirmed from the ambulance’s
simulated edge and lane transition, with a timeout detecting a missing or stalled vehicle. The intersec-
tion then enters recovery and either completes a bounded compensation plan or returns control at a safe
phase boundary. A revised route cancels obsolete future requests before new look-ahead activation, pre-
venting two route versions from competing for a signal. These choices follow the transition and recovery
emphasis in emergency-preemption research [19] while keeping all timing values as simulation policies
rather than certified field parameters.

5.8.2   Scenario Assignment and Repetition

The evaluation manifest will define demand levels, origin-destination pairs, incident timing, dispatch
time, warm-up, measurement horizon, and repeated seeds before final runs. Every controller receives
the same requested set, and actual departures are retained when congestion changes insertion feasibility.
The number of repetitions is chosen using pilot variance and available computation, then disclosed rather
than retroactively reduced to favorable cases. Results include variability through standard deviation or
confidence intervals, with paired differences used when runs share a demand seed. Reinforcement-
learning training and hyperparameter selection use only training and tuning scenarios. Held-out demand
combinations and at least one unseen seed set remain reserved for final evaluation, while perception
data is split by source or continuous sequence to reduce temporal leakage. Failures, timeouts, infeasible
routes, and safety-filter interventions remain in the run inventory and are reported separately when ag-
gregation would be misleading. These rules preserve the distinction between incomplete implementation
evidence and an evaluated negative result.

5.8.4   Reproducibility Package

Each run will retain the source revision, dependency manifest, SUMO version, network and route check-
sums, controller and model version, full configuration, seed, logs, metric schema, and terminal reason.
Applied decisions are stored separately from controller requests, and route revisions identify the cost
snapshot and trigger that produced them. Large external video and pretrained weights may be refer-
enced by a license-aware URI and checksum when redistribution is not permitted. A script should
recreate a run from its manifest, and every manual NetEdit change must be committed as a versioned
network artifact rather than left in an operator’s local state. Derived plots and summary tables retain
their source run identifiers and analysis-script revision. Failed and cancelled runs keep their partial logs
and explicit terminal state. This package does not guarantee identical hardware timing, but it makes
scenario semantics, causal events, and analytical transformations inspectable enough for another team
member to reproduce the experiment or explain a difference.



5.9     Threats to Validity

Construct validity is threatened when a queue proxy, waiting-time implementation, or reward compo-
nent does not represent the concept named in the report. Definitions and units are therefore versioned,
and image-space proxies are not relabeled as physical quantities without calibration. Internal validity
can be weakened by unmatched demand, different warm-up, hidden seed changes, or controller-specific
CHAPTER 5. PROPOSED APPROACH AND METHODOLOGY                                                             57


failures; paired manifests, one measurement implementation, and retention of failed runs reduce these
risks. External validity remains limited by synthetic demand, map inaccuracies, SUMO car-following
assumptions, a small selected network, and domain shift between public video and Lahore traffic. Con-
clusions will be bounded to the tested network, demand families, software versions, and video sources,
with no claim about clinical response time or public-road safety. Conclusion validity can be weakened
by too few repetitions, test-set tuning, selective failure removal, or reporting only means. Pilot variance,
held-out scenarios, paired comparisons, variability, and sensitivity analysis address those concerns. If
statistical tests are used, their assumptions and effect sizes will be reported; significance alone will not
establish practical value.



5.10     Conclusion

The methodology specifies a staged progression from validated measurements and baselines to inte-
grated emergency control. Network provenance and demand manifests support repeatable scenarios;
source-separated video evaluation prevents perception estimates from being confused with simulator
truth; and common safety constraints permit a fair controller comparison. Routing uses time-consistent
nonnegative costs, validity checks, and hysteresis, while the corridor lifecycle makes request, clearance,
active priority, passage, cancellation, and recovery observable. The comparison matrix separates per-
ception, normal control, routing, corridor effect, and robustness so the cause of a result can be explained.
Held-out scenarios, repeated seeds, explicit metrics, retained failures, and reproducibility artifacts pro-
tect the final evaluation from undocumented tuning. Most importantly, the procedure allows a learned
controller, tracker, rerouting policy, or corridor configuration to produce a negative or mixed finding
without prompting selective changes to the test protocol. The next chapter maps these methodological
responsibilities to components, interfaces, state ownership, and failure handling.

Chapter 6 High-Level and Low-Level Design

This chapter maps the requirements and methodology to a service-oriented prototype design that can
be implemented incrementally on the team’s available machines. The decomposition protects experi-
mental determinism by assigning the simulation clock and all signal actuation to one adapter. The API,
dashboard, perception worker, controllers, routing logic, and experiment store exchange typed mes-
sages without competing for that authority. The design also separates a requested decision from the
action applied after safety checks, preserves the source and effective time of every traffic snapshot, and
binds corridor requests to an immutable route version. These choices support replay and fault diagnosis
without requiring a prematurely distributed deployment. Interfaces may initially be implemented as in-
process modules, provided that they retain the same ownership boundaries and contracts. The chapter
moves from architecture and domain objects to interaction sequences, state transitions, data contracts,
synchronization, failure handling, module policies, and testing so each important requirement has a
visible design consequence.



6.1    System Overview and Design Goals

The system must support repeatable research runs, an interactive demonstration, and post-run analysis
without allowing presentation concerns to alter experimental state. Its main design goals are determin-
istic ownership of state changes, replaceable controller and perception implementations, explicit time
and units, safe corridor transitions, immutable run configuration, and visible failure. Performance is
optimized only after these properties are preserved because a faster result is not useful when its source,
phase legality, or causal order is uncertain. The design assumes one machine or a small development
deployment for Deliverable 2 and FYP-I. Logical separation therefore does not imply a network service
for every box in the diagrams. The orchestrator, controllers, routing logic, and repositories may begin
as in-process modules behind typed interfaces, while video inference can move to a bounded worker
when profiling shows it would block the control loop. This approach keeps deployment manageable but
preserves a path to isolate resource-heavy components without changing experimental semantics.

because inference, rendering, and storage latency can vary independently of simulated time. A snapshot
identifies the step at which its values became effective, and an applied signal event records the step at
which the adapter enacted it. Route revisions and priority events are enqueued in an order that prevents
an old request from being interpreted as current. Missing values remain missing rather than being
converted to zero, and unknown schema versions are rejected rather than partially decoded. These rules
give the fields in Table 6.3 operational meaning and support replay, stale-data handling, and comparison
across runs without assuming perfectly synchronized wall clocks. They also allow a delayed write to be
distinguished from a delayed decision.



6.9    Concurrency, Synchronization, and Resource Ownership

The orchestrator is the only writer to simulation time, and TraCI access is serialized behind the adapter.
Controller computation receives an immutable snapshot and returns a request rather than holding a
reference to mutable global state. Perception uses a bounded work queue; if inference falls behind, the
worker marks observations late or drops work according to a recorded policy instead of blocking control
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                                68


indefinitely. Dashboard streams are lossy views, so a slow client may skip intermediate snapshots but
cannot delay decisions. Run configuration becomes immutable after start. The current route version is
updated atomically with cancellation of obsolete corridor requests, preventing new and old paths from
owning priority concurrently. Database writes may be batched where safe, but an applied signal event or
mission transition is not acknowledged until it has entered a durable bounded queue. During shutdown,
the API stops accepting new commands, the orchestrator ends or detaches SUMO safely, queued records
are flushed, and the run receives an explicit completed, stopped, failed, or incomplete terminal state.



6.10     Error Handling and Fallback

Table 6.4 defines immediate containment and retained evidence for failures at each major boundary. A
SUMO or TraCI failure stops decision-making because continuing to show live state would be mislead-
ing, whereas a dashboard disconnect leaves the authoritative experiment unaffected. Stale observations
and invalid controller requests are rejected or handled through a declared simulator or fixed-control
fallback, and every interval using that fallback is marked so it cannot be included silently in a clean
learned-controller aggregate. A missing route prevents partial corridor activation, while a lost ambu-
lance or timeout cancels future priority and moves active intersections through recovery. Persistence
uses a bounded buffer only long enough to tolerate a transient issue; the run stops before evidence loss
grows without limit and is marked incomplete if durability cannot be restored. These policies favor an
explicit failed run over an apparently successful record whose causal events are missing. Fault-injection
and small-network integration tests will verify both the immediate behavior and the final recorded state.

6.11       Detailed Module Policies

6.11.1     Controller Policy

All controllers implement a common method that accepts an immutable traffic snapshot, intersection
configuration, and decision context, then returns a request with explanation fields. They cannot write
global state, call TraCI, or suppress the record of a rejected action. The fixed controller, pressure-
inspired controller, and learned policy therefore differ in decision logic while sharing phase identifiers,
decision intervals, safety constraints, and applied-event recording. Deterministic evaluation disables
exploration and seeds every permitted stochastic operation. The safety filter verifies phase membership,
minimum green, required clearance, maximum priority duration, and current ownership before an action
reaches the adapter. If a policy is unavailable or repeatedly invalid, control transfers at a legal boundary
to the configured baseline and the affected interval is marked. This common interface is central to a
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                             70


fair comparison because it prevents one controller from receiving more permissive movements or direct
simulator privileges. Explanation fields are retained for later error analysis.


6.11.2      Routing Policy

The graph builder derives nodes and edges from validated SUMO vehicle movements, including allowed
classes and turn continuity. Cost providers are composable but must state units, observation time, fall-
back behavior, and whether link travel time already includes queue delay. This metadata prevents the
routing service from adding overlapping estimates or comparing seconds with an unnormalized conges-
tion score. A published route plan is immutable, and the mission points to exactly one current version.
Revisions are accepted only through Algorithm 1, which compares paths under one cost snapshot and
applies feasibility, hysteresis, persistence, and cooldown rules. A hard closure overrides ordinary cost
and invalidates an affected remaining path immediately. Before publication, the route is checked from
the ambulance’s current edge to the destination and given a revision cause. The routing service never
actuates signals; it supplies versioned plans to the corridor coordinator, which can then cancel or create
priority requests consistently.


6.11.3      Persistence Policy

The store uses schema migrations and referential constraints for structured configuration, events, mis-
sions, routes, and metrics, while large videos, model files, and logs may remain checksummed external
artifacts with provenance. Raw high-frequency state can be downsampled for persistence only when
the sampling interval and aggregation rule are recorded in the metric definition. Completed run con-
figuration is immutable, and derived summaries retain their source run identifiers and analysis version.
Secrets, machine-specific credentials, and unportable local paths are excluded from research exports;
licensed artifacts are referenced rather than redistributed when necessary. PostgreSQL is proposed for
structured records, but implementation may begin with a file-backed engine behind the same repository
interface. The domain schema and integrity rules remain independent of that choice so a storage migra-
tion cannot change the meaning of an experiment. A persistence failure follows the bounded behavior in
Table 6.4 rather than silently discarding events. Recovery records state whether buffered evidence was
restored.


6.11.4      User-Interface Policy

The user interface is a view and command boundary, not a second control plane. Colors are supple-
mented with text and symbols so congestion, corridor state, or failure is not conveyed by color alone.
Values display their units, source mode, freshness, and invalid state where applicable. Schematic predic-
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                                71


tions remain visually distinct from measured results, and an uncalibrated video proxy is not labeled as a
physical queue or speed. The interface does not display “time saved” until a valid reference run exists
under the same comparison manifest, and it exposes configuration differences when direct comparison
is unsafe. Commands receive validation errors tied to fields, while connection loss leaves the experiment
running and allows a client to reconnect from the current event cursor. These policies implement the
wireframe intentions in Section 4.7 and ensure that a polished display cannot conceal stale data, fallback
intervals, missing runs, or incomplete evidence.



6.12     Testing Strategy

Unit tests cover cost functions, route continuity, hysteresis, metric calculations, schema validation, fresh-
ness rules, and corridor transition guards. Property or invariant tests generate action sequences to ensure
incompatible greens are never requested for application, one component owns each intersection, obsolete
route versions cannot activate priority, and cancellation eventually reaches IDLE through RECOVERY.
Integration tests use small SUMO networks to validate single-step ownership, detector-to-state mes-
sages, route application, fallback, and persistence ordering. Scenario tests replay fixed seeds for normal
control, closure rerouting, no-route, invalid actions, stale data, controller loss, ambulance timeout, per-
sistence failure, and dashboard disconnect. Contract fixtures allow components to be replaced by stubs
without weakening field validation. Research verification remains separate from software correctness:
passing these tests shows that the implementation follows its specification, but it does not establish
that a policy improves traffic or emergency travel. The matched experiments in Chapter 5 provide that
evidence, while test results explain whether a failed experiment reflects the policy or a software defect.



6.13     Coding, Build, and Maintainability Policies

Python modules will use static type hints, consistent formatting and linting, bounded dependency ver-
sions, structured logging, and documentation for public interfaces. React components separate data
acquisition from presentation so a visual revision cannot change experiment ownership. Configuration
is stored in validated versioned files rather than scattered constants, and secrets remain outside exported
manifests. Continuous checks should run unit tests, schema validation, and a minimal headless SUMO
scenario before a revision is used for evidence. Experiment releases are tagged and their commit iden-
tifier is written into each run manifest. The intended repository structure separates application services,
controllers, routing, perception, simulation, dashboard, contracts, scenarios, and experiment artifacts.
This is a proposed organization, not evidence that all directories or services already exist. Small inter-
faces allow a tracker, learned policy, database engine, or dashboard transport to change without rewriting
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                                               72


the central loop, while versioned contracts force such changes to declare any effect on recorded evidence.



6.14     Conclusion

The design assigns one clear owner to every mutable resource and makes observation source, simulation
time, units, route version, requested action, and applied action explicit. The high-level architecture keeps
presentation and perception outside the single-writer simulation path, while component responsibilities
and data contracts make integration boundaries testable. The domain model and sequences preserve
causal links from scenario and snapshot through controller request, safety decision, route revision, cor-
ridor transition, and durable event. Guarded recovery and bounded fallbacks ensure that a failure does
not leave an unexplained signal or apparently live dashboard. Common controller interfaces support the
intended progression from fixed and pressure-inspired baselines to a learned policy, and versioned rout-
ing enables a moving corridor without granting the pathfinder direct signal authority. The architecture is
modular enough for team implementation on one machine and leaves distribution as a profiling decision,
not an assumption. It also preserves failed runs and negative research outcomes as evidence instead of
hiding them behind interface behavior.
